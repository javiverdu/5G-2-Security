## 1. Deployment procedure

The topology is built by one idempotent script, `scripts/deploy/setup.sh`, which:

1. creates the `ue`, `access` and `core` namespaces;
2. wires three veth pairs (`ue↔access`, `access↔core`, `core↔host`);
3. assigns the planned addresses, brings links up and enables IP forwarding;
4. installs the routing entries;
5. creates the Docker bridge `datanet` (`10.0.4.0/24`) and starts `nginx-app` and `iperf3-srv`;
6. applies the two host firewall fixes required by Docker 29 (see §5).

Teardown is `scripts/teardown/cleanup.sh`. All raw output in `results/step1/` is
regenerated by `scripts/deploy/collect-step1-evidence.sh` (run it as root; see §6).

### Role mapping — why three namespaces plus Docker

The assignment suggests namespaces `ue`, `access`, `core`, `app`, etc. This design
implements the first three as Linux namespaces and realises the **`app` role as the
host root namespace plus the Docker bridge `datanet`**, where the services actually run:

| Reference role | Implementation | Evidence |
|---|---|---|
| UE / client | Linux namespace `ue` | [`01-namespaces-interfaces.txt`](../results/step1/01-namespaces-interfaces.txt) |
| Access router | Linux namespace `access` | idem |
| Core / gateway | Linux namespace `core` | idem |
| App server / Data Network | host root namespace + `datanet` bridge + `nginx-app` (10.0.4.10) and `iperf3-srv` (10.0.4.20) | [`03-docker-network.txt`](../results/step1/03-docker-network.txt), [`04-listening-ports.txt`](../results/step1/04-listening-ports.txt) |

The `app` role is implemented with Docker rather than a fourth `ip netns`
deliberately: (1) it is a **real application server** with real transport ports,
not a simulation; (2) the bridge provides its own embedded DNS (`127.0.0.11`,
visible in `04-listening-ports.txt`); (3) the Data Network boundary is represented
by `host:veth-hn` (10.0.3.2) ↔ gateway `10.0.4.1`. The path remains **routed, no
NAT**, so the observed addresses are end-to-end. The four-hop chain
`ue → access → core → host → app` is equivalent to `ue → access → core → app`.

## 4. Path explanation (packet evidence)

The ICMP reply TTL decreases by exactly one per routed hop, proving each stage
forwards the traffic ([`05-e2e-ping.txt`](../results/step1/05-e2e-ping.txt)):

| Target | TTL | Interpretation |
|---|---|---|
| `10.0.1.1` (access) | 64 | directly connected |
| `10.0.2.2` (core) | 63 | 1 routed hop (access) |
| `10.0.3.2` (host) | 62 | 2 routed hops (access, core) |
| `10.0.4.10` / `10.0.4.20` (containers) | 61 | 3 routed hops (access, core, host) |

Forward path of an HTTP request `10.0.1.10 → 10.0.4.10:80`:
`ue` (default → `10.0.1.1`) → `access` (`10.0.4.0/24 via 10.0.2.2`) →
`core` (`10.0.4.0/24 via 10.0.3.2`) → host (`10.0.4.0/24` on the bridge) →
`nginx-app`. The return path mirrors it
(container → `10.0.4.1` host → `10.0.1.0/24 via 10.0.3.1` → core → access → `ue`).
Routing is symmetric, so the (loose) `rp_filter` checks pass on every hop.

**Packet-level proof of the same path.** Step 2 captures identical traffic at six
points along this path (`ue`, `access:eth0/eth1`, `core:eth1`, `host:veth-hn`, the
container) and records **identical packet counts at all six**
([`cross-point-packet-counts.txt`](../results/step2/cross-point-packet-counts.txt)),
demonstrating that every packet is generated, forwarded by both routers and the
host, and delivered. Raw `.pcap` files live in `captures/step2/` (git-ignored —
ship them alongside the repository) and the dissections in `results/step2/`. A
minimal packet path for Step 1 itself is produced by
`collect-step1-evidence.sh --with-capture`.

## 5. Diagnosis — Docker 29 hardened forwarding

The first end-to-end attempt worked up to the host but failed on the last
segment (`ue → containers`), even though the host route to `10.0.4.0/24` existed.
Multi-point captures (`core:eth1`, `host:veth-hn`, bridge) showed requests
arriving at the host but never entering the bridge. Two Docker-default layers
were responsible:

1. **raw/PREROUTING drops per container IP.** `table ip raw` contained
   `drop` rules for `10.0.4.10/10.0.4.20` arriving from any interface but the
   container bridge, so packets were discarded *before* FORWARD (all FORWARD
   counters stayed at 0; `nstat` showed `IpInReceives` rising without
   `IpForwDatagrams`). The rules reappeared after every `docker network (re)create`.
   A binary wrapper on `iptables` proved the origin: **`dockerd` itself** programs
   them (Docker ≥ 28 hardening against direct routed access to container IPs).
   **Fix:** `"allow-direct-routing": true` in `/etc/docker/daemon.json`, applied
   idempotently by `setup.sh`.
2. **Filter-layer drop.** Docker sets `FORWARD` policy `DROP` and adds
   `DROP all !br-<id> br-<id>` in the `DOCKER` chain. **Fix (documented extension
   point):** `iptables -I DOCKER-USER -i veth-hn -d 10.0.4.0/24 -j ACCEPT`;
   counters confirm this rule carries the data path
   ([`08-firewall-state.txt`](../results/step1/08-firewall-state.txt)).

Both fixes are integrated in `setup.sh` and reversed in `cleanup.sh`.

## 6. Reproduce

```bash
sudo ./scripts/teardown/cleanup.sh   # optional clean start
sudo ./scripts/deploy/setup.sh       # deploy everything
sudo ./scripts/deploy/verify.sh      # all checks must pass
sudo ./scripts/deploy/collect-step1-evidence.sh               # regenerate raw evidence
sudo ./scripts/deploy/collect-step1-evidence.sh --with-capture # + packet-level path
```

> **Why `sudo`?** `nsenter -t <pid> -n`, used to read each container's listening
> sockets, requires `CAP_SYS_ADMIN`. Run as a normal user it fails with
> *"fallo al volver a asociar al espacio de nombres: Operación no permitida"*.
